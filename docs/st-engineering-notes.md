## 1. 架构选择：为什么不是全片上流式

**结论：Ti60 上做风格迁移，瓶颈是片上存储，不是 DSP。**（docs/archive/st_480p_progress.md）

- ink_dw 原网络做 640×480 全片上流式，估算需要约 1.2 MB：
  - 行缓冲 396 KB；
  - 分支 FIFO 737 KB，其中长 skip 约 590 KB；
  - 上采样 46 KB；
  - 权重 50 KB。

  而 Ti60 的 RAM 总共 256 块 10 Kbit，约 320 KB，扣掉 SoC、DDR 控制器、帧缓冲后只剩约 88 块。
  实测 160×120 的版本就要 413 块 RAM10。
- 流式第一版 40×20 的综合结果里，DSP 158 个，其中 **requant 占了 102 个，真正做 MAC 的只有 56 个**。
  改成共享 requant、小 FIFO 改移位寄存器、ROM 改同步宽字之后，DSP 降到 101，RAM 从 474 降到 331，还是放不下。
- 最后选的路线是 **DDR 多 pass 块引擎**：每个 pass 从 DDR 读一个张量，在片上做 DW→PW（可以带 LN/FiLM/残差相加），结果写回 DDR。
  - 片上只需要几行的行缓冲。
  - 跳连和中间张量都放在 DDR。
  - 代价是 DDR 带宽，每帧约 49 MB。

  这套 pass 引擎后来也正好容纳了 GAP + FiLM 这种"整帧统计 → 下一个 pass 用"的结构（见第 3 节）。

## 2. 视频通路上的坑

| 现象 | 根因 | 处理 | 出处 |
|---|---|---|---|
| 720p binning 下块状错位、异色竖条、曝光跳动 | 把厂商 binning 表的 PLL 换成 1080p 的值，或者在 1080p 表上只打开 binning 开关。数字水平合并和时钟、模拟时序不配套 | 完整保留厂商 binning 的 PLL 和模拟时序，只改 lane 相关的两个寄存器 | docs/720p_binning_black_screen_issue.md |
| 灰色画面，红绿行条纹，每帧只有 540 行 | HTS=1500 时，4-lane MIPI 每行的发送时间不够，传感器每 4 行丢 1 行 | HTS 1500 → 2048 | 同上 |
| 画面最左边约 1/120 宽的竖带显示的是最右边的内容 | `layer_fetch` 的 FIFO 跨帧残留 1 个 beat。每帧产生和消费的数据量恰好相等，所以残留永远排不空。1 beat = 16 像素 = 1920 的 1/120 | 每帧在场起始处清空 FIFO 的指针和计数。只清数据没用，残留的是"位置"而不是"内容"。之前七次尝试都没打到这个点 | docs/archive/video_readside_refactor_issue.md |
| 分屏画面闪烁，坏行计数在涨 | 加速器的 AXI 主口在仲裁里优先级最高，它连续发 128-beat 突发，显示读口等到 STARVE 超时，合成器欠载 | 外部主口改成最低优先级 | 5d3aa05 |
| 加速器在综合后整个消失 | `vid_rst_n` 没有声明，generate 块里生成了一个没有驱动的隐式 net，加速器一直处于复位，被综合器删掉 | 在 generate 块前面声明这些线 | a4c01d0 |

报告里可以写的经验：
- 跨帧的状态（FIFO 残留、累加器）一定要在帧边界显式清零。第 5 节的 GAP bug 是同一类问题。
- 共享 DDR 的系统里，实时显示必须优先于计算。
- SystemVerilog 的隐式 net 很危险，建议加 `default_nettype none`。

## 3. guided 网络在硬件上的形态

docs/st-guided-adr.md 有完整的 pass 表。要点如下：

- **分辨率分层**：
  - 网络在 640×360 上运行（对 1280×720 做 2×2 box 平均，输出做 2×2 复制）。
  - 主干在 H4 = 160×90 上，80 通道。
  - 引导分支保留 H（640×360）和 H2 的细节。
- **13 个 pass**，包括：
  - pool；
  - guide（宽 im2col，每像素 2 拍）；
  - stem、h2g（拆成两个单层 pass）；
  - enc0、enc1、res_a、res_b；
  - dec_h4（LN）；
  - dec_h2（带 GAP tap）；
  - MLP；
  - film；
  - head。
- **整数化定义**：
  - LN 的 1/√D 用 768 项 LUT 加指数 e 实现，一个归一化不需要除法器。
  - FiLM 是先对 GAP 和求和，再用一个整数 MLP 得到每个通道的 mul/off。
  - 这些定义都是先在 Python 里定好、验证精度（≤0.08 dB），再写 RTL。
- **GAP + FiLM 刚好适合 pass 引擎**：
  - 在 dec_h2 写 DDR 时，顺路累加每个通道的和。
  - 这个 pass 结束后，用串行 MLP 算出系数（4501 周期，1 个 DSP），写进 st_norm。
  - 下一个 film pass 直接使用。
  - 全帧统计没有额外读一遍 DDR。

### 周期剖析（仿真 6,413,390 周期）

- enc1、res_a、res_b 各约 723k 周期，PW 阵列满载，是真正的计算瓶颈。
- guide、h2a、h2b、film 合计约占 30%，它们受每像素吞吐限制。
  - h2b 每像素 10 周期，理想值约 5，是现成的优化点。
- 板上每帧约 6.8M 周期，比仿真多约 6%，多出来的是 DDR 争用。

### guided 结构值不值（分析结论）

- 计算量和资源大头都在 H4 的 80 通道主干上。引导分支用很少的通道把 H、H2 的边缘细节带回来，所以高分辨率部分很便宜。
- FiLM 给了一个全局风格调制的入口，后来也成了多风格切换最自然的位置（第 7 节）。
- "输入改成 Y/C 两平面能省很多资源"这个想法不成立：
  - 输入通道只影响最前面几个 pass，而且 im2col 按 16 字节一拍打包，27 个元素降到 18 个仍然是两拍。
  - 资源大头在 80 通道主干，跟输入通道数无关。

## 4. 资源压缩：Efinity / Ti60 的特性和坑

最后一版 XLR 用了 98.1%，RAM 一块不剩。每块 RAM 都是抠出来的，这部分经验最多。

### RAM10 的形状和推断规则

- RAM10 的可用形状：256×40、512×20、512×16、2048×5 等。**一次读最多 20 位**（512×20），所以位宽决定块数：
  - rq 字从 64 位压到 48 位（bias、尾数、指数分开存），13 → 10 块（fa6f759）。
  - 再改成一个 196 位的行镜像、用一次 `$readmemh` 加载，13 → 10 块（3ba60e0）。
  - bias 改 16 位，10 → 9 块（71d946b）。
- **非 2 的幂深度会先向上取整再切分**：2560×40 的行缓冲按 4096 深计，用 20 块。拆成 2048 + 512 两个 bank 后只要 10 块（cc2676c）。
- **Efinity 会自己挑形状，未必最省**：80 位宽的数组被映射成 512×16 × 5 块。
  拆成 4 个 20 位的存储器后是 4 块，RAM 257 → 256，刚好放下（c27253f）。
- **ROM 内容只认直接写在数组上的 `$readmemh`**，绕一层就推断不出初值。
- **大的未打包数组会被映射成 RAM**，即使你想要寄存器。PW 的累加器改成扁平向量才保持为寄存器（d5bfc5c）。
- **带动态下标的宽 bank 数组会让 efx_map 段错误**：4 个 640 位 bank 的数组配上动态读下标，映射器直接 SIGSEGV。改成 4 个具名向量加两级 mux 后正常（2ca6ce8）。

### 寄存器和 LUT

- **Ti60 没有分布式 RAM，但有 SRL**：
  - DW 的列延迟线从寄存器改成 SRL 延迟线，配合 bank 化的行 RAM，FF/LUT/RAM 从 6869/7547/77 降到 2514/5153/51（cc2676c）。
  - st_film 的 GAP 和用"新像素覆盖"代替同步清零，于是能映射到 SRL：1836 FF / 4142 LUT → 664 FF / 1082 LUT。
    代价是 `gap_clear` 必须跟着一个像素才生效，这正是后面 GAP bug 的伏笔（第 5 节）。
- **用 tag 代替数据**：PW 的 tile FIFO 原来存 8×512 位的 requant 字。改成只存 8 位 tag，出队时再查 rq ROM，省掉 8×732 FF 和一个 732 位 8:1 mux（973b2ec）。
- **权重寄存器不要重复一份**：PW 原来的 `w_cur` 和 MAC 阵列内部的操作数寄存器是重复的。
  给 `st_mac8x16` 加一个 `in_wld` 使能，让阵列自己的寄存器装权重，LUT −411（e615df3）。
- **FIFO 深度是性能参数，单元测试看不出来**：
  - tile FIFO 深度从 8 改成 2，单元测试周期不变（−1152 FF），但整引擎在 DMA 反压下从 6.41M 变成 8.34M 周期。
  - 最后用 4（−768 FF，周期不变）。
  - 单元测试没有反压，必须用整引擎测试来定 FIFO 深度（541b925、50781a1）。
- st_unpack 去掉 10 拍的像素缓冲，只保留 hrep 需要的一拍，FF 1390 → 352（6710f47）。

## 5. 仿真全过，上板才出问题的两个 bug

这两个 bug 都是本阶段最有价值的经验。

### 5.1 黑屏，PROC 帧数为 0（c27253f 引入，1aa0638 修复）

- **现象**：把 st_post 的 80 位行缓冲拆成 4 个 20 位存储器之后，仿真全部通过，上板黑屏，处理帧计数为 0。
- **定位**：在板上二分。e615df3 正常，加上 ISP 改动也正常，问题落在 st_post 这一次提交上。
- **根因**：拆分后的 4 个存储器共用一个组合读出，再打进一个共享的寄存器。
  这个写法在仿真里语义正确，但 Efinity 没能把它推断成"带输出寄存器的 RAM 读"，生成了错误的读逻辑。
- **修复**：每个存储器在自己的 always_ff 里做 `if (en) q <= mem[a]`。
- **经验**：在 Efinity 上，RAM 必须严格按推断模板写（同步读，并且读寄存器和存储器在同一个块里）。
  仿真通过不能说明综合结果正确。

### 5.2 输出色调随时间循环变化（cfb1faa 修复）

- **现象**：画面内容不变，风格化输出的整体色调却一直在缓慢轮回。
- **根因**：
  - st_film 的 `fresh` 标志（下一个像素覆盖旧和，而不是累加）原来写在 `else if (tap_valid || gap_rot)` 分支里。
  - 引擎打出 `gap_clear` 的那个周期恰好没有 tap 拍，于是这次清零丢了。
  - 结果 GAP 和跨帧一直累加，FiLM 系数逐帧漂移，加上回绕，看起来就是色调循环。
- **为什么仿真没发现**：tb_st_film 每次只跑一个平面（单帧）。
  改成连续 3 轮、每轮前打一次 `gap_clear` 之后，旧代码立即失败（第二轮的和是两倍）。
- **经验**：
  - 有状态的模块（累加、统计、跨帧寄存器）至少连续测 3 帧。
  - 控制脉冲和数据拍不在同一周期的情况要专门测。
  - 这类 bug 的表现是"随时间变化"，单帧对 golden 永远是对的。

## 6. RGB565 的数值细节

输入（ISP → DDR）和输出（PROC → 显示）都是 RGB565。

- **输入抖动的偏置**：
  - 旧的 ISP 量化是 `min(R + 2t + 1, 255) >> 3`。解包时用高位复制回 8 位，两者叠加，R/B 最多偏 +6、平均偏 +4，画面整体偏亮。
  - 新公式 `r5 = (31R + 32 + 64t) >> 8`、`g6 = (63G + 32 + 64t) >> 8` 是按 31/255、63/255 的真实比例量化，偏置在 −2..+1 以内（683bce6，`sim/ref/isp_ref.py` 同步修改）。
- **输出抖动**：
  - 网络输出是 8 位，直接截成 565 会产生色带。
  - st_post 在 2×2 复制时，把截掉的小数部分按 2×2 有序抖动分摊到 4 个像素上：R 用 1/4 步，G、B 用 1/2 步。
  - 块平均误差：R 7 → 1.75，G 3 → 1.5，B 7 → 3。
  - 这是利用 2×2 复制"白送"的空间做抖动，不增加任何存储。
- **对训练的影响**：
  - 训练端 guided.rs 的 `input_quant="rgb565"` 和硬件量化公式要一致。
  - 输入偏置修正以后，565 输入感知训练的收益已经不大。输出抖动则完全在训练之外。

## 7. 多风格

方案对比见 docs/st-multistyle-packets.md，实际部署见 docs/st-multistyle-deploy.md。要点：

- 卷积全部共享。每个风格只换 LN 的 γ、β（80 通道）和 FiLM MLP，每个风格约 2.3 KB。
- 走方案 B：
  - LN 系数按 `style × 20` 行偏移存在 coef_ram 的空闲区；
  - FiLM ROM 每个风格 512 行；
  - `ui_style` 在每帧开始时锁存。
- 2 个风格（whitebox + sky）已上板（82f4c34），14.8 fps。
- 多出来的 2 个 RAM10 靠 `fifo_srl_core` 腾出：st_add、st_norm 的 16 深 FIFO 改用 SRL，省 4 块。fifo_sync_core 按 40 位切片不省 RAM。
- FiLM 的移位常数所有风格共用，取各风格的最小值；C0/KB 由联合校准的 scale 决定，所有风格相同。
- 训练端的整数导出仍然拒绝 styles > 1，所以在外部先拆成单风格、联合校准、分别导出，再合并。

## 8. 开发方法

- **golden 先行，逐位比对**：
  - 每个数值定义先在 `tools/st_guided.py` 里实现，并和 fp32 对比精度。
  - 然后由生成器产出 ROM、pass 表和测试向量。
  - 每个 RTL 模块的 testbench 都和 golden 逐位比较，整引擎 tb_st_engine 跑完整的 13 个 pass。
- **多 agent 并行写模块**：
  - 用 omp 在独立 worktree 里并行做 st_dw、st_pw、st_norm、st_film、st_unpack/pack、pre/post 等模块。
  - 每个任务都写明接口、资源目标和必须通过的测试。
  - 集成和板上验证由主线完成。
  - 资源压缩阶段同样按模块并行，各自给出 map 前后的对比。
- **板上二分**：仿真找不到的问题，用临时 worktree 编译中间版本，JTAG 加载，用 `tools/board_smoke_test.py` 读 UART 遥测（处理帧数、错误、周期），比看屏幕更快、更客观。
- **度量驱动**：每次压缩都以 `efx_run -f map` 的 res.csv 模块行做前后对比，并记进提交信息。
  所以本文的大部分数字都能在 git log 里查到。
