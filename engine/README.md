# E5c: Efinity project for `engine_top` on Ti60F225

Goal: turn the *projected* Ti60F225 resource numbers of `docs/engine/e5_resources.md`
into *measured* numbers, or record exactly why that is not possible.

| item | value |
|---|---|
| vendor tool | Efinity 2026.1.132 (`/opt/efinity/2026.1`), CLI `/usr/bin/efx_run` |
| device | Titanium `Ti60F225`, timing model I3, package 225-ball FBGA |
| RTL under test | `../../fpga_rtl_lab/target/*.sv` - generated by `veryl build`, **read-only** |
| top | `engine_top` (`engine_top.sv`) |
| clock          | no SDC used; `efx_pnr` auto-constrains the clock port to 1 ns and reports the maximum achievable period |

Nothing in `../../fpga_rtl_lab/` is modified by this project: `synth.f` points at the
generated sources and every output lands in this directory.

## 1. Exact command sequence (reproducible)

```sh
cd fpga_src/engine
sh run.sh map        # synthesis only            -> outflow/
sh run.sh compile    # map + place & route + STA -> outflow/
```

`run.sh` runs, verbatim:

```sh
/usr/bin/efx_run engine_top --family Titanium --device Ti60F225 --timing_model I3 \
    -f "$FLOW" --flist synth.f --output_dir outflow --work_dir work_syn
```

A single-module run uses the same command with a one-line file list, e.g.:

```sh
/usr/bin/efx_run tile_reader --family Titanium --device Ti60F225 --timing_model I3 \
    -f compile --flist synth_tile_reader.f --output_dir out_leaf_tile --work_dir work_leaf_tile
```

Note: `-f full` is **not** usable on this machine - it starts with an iverilog RTL
pre-check and Efinity's bundled `ivl` aborts with
`/usr/lib/ivl/ivl: /opt/efinity/2026.1/lib/libstdc++.so.6: version CXXABI_1.3.15 not found`
(see `run_full.log`). `-f compile` and `-f pnr` are used instead. `--pnr_opts=--sdc_file=X`
is rejected by `efx_run_pnr.py` argparse (`argument --opt: expected at least one argument`),
so timing uses the tool's own default clock constraint; see section 6.

## 2b. Ti60F225 after the fix (t15): map and PnR both complete

`src/conv_stream.veryl` no longer writes a byte lane inside a wide RAM word: the
packed weight word is assembled in the `wr_sh` register and the RAM is written as
one full word (`wr[ld_word_c[WW-1:0]] <= wr_nx;`). With that one structural change
(`sh run_fixed.sh Titanium Ti60F225 I3 ti60`):

```
map exit=0 root=Top-level Entity Name : engine_top
pnr exit=0        (pnr : PASS)          <-- was: assert exit 12 / SIGSEGV
```

| measured on Ti60F225 | value | report |
|---|---|---|
| logic elements (XLRs) | **25,384 / 60,800 (41.75 %)** | `out_ti60/engine_top.place.rpt` |
| FF / LUT4 / ADD | 8,484 / 16,194 / 4,026 | `out_ti60/engine_top.map.rpt` |
| RAM blocks (10 Kbit) | **78 / 256 (30.47 %)** | `out_ti60/engine_top.place.rpt` |
| DSP blocks | **50 / 160 (31.25 %)** = 17 `EFX_DSP48` + 33 `EFX_DSP24` | `out_ti60/engine_top.place.rpt` |
| Fmax, timing model I3 | **43.601 MHz** (22.935 ns, R-R) | `out_ti60/engine_top.timing.rpt` |
| Fmax, timing model C4 | **49.667 MHz** (20.134 ns, R-R) | `out_ti60_c4/engine_top.timing.rpt` |

Per module (`out_ti60/engine_top.hier_util.rpt`; XLRs in parentheses are
combinational-only):

| module | XLRs | RAM | DSP | FF |
|---|---|---|---|---|
| `engine_top` | 25,384 (714) | 78 | 50 | 8,484 |
| `layer_seq` incl. children (`+seq`) | 24,187 | 78 | 49 | 8,230 |
| `conv_stream` (`+dut`) | 15,021 | 78 | 37 | 6,152 |
| `tile_reader` (`+rd`) | 5,733 | 0 | 2 | 640 |
| `point_add` (`+padd`) | 483 | 0 | 1 | 149 |
| `requant_unit` x2 inside conv_stream | 413 + 401 | 0 | 2 + 2 | 8 + 15 |

**One caliber, stated once.** The map report counts cells (`EFX_LUT4`, `EFX_FF`,
`EFX_ADD`), the packer counts XLRs, and here they are the *same* cells: `EFX_FF`
8,484 = 3,221 (LUT4+FF) + 101 (Adder+FF) + 5,162 (FF) and `EFX_ADD` 4,026 =
3,925 (Adder) + 101 exactly, `EFX_LUT4` 16,194 ~ 12,975 (LUT4) + 3,221 (LUT4+FF)
(`hier_util.rpt` is an estimate, hence the `~`); the five categories sum to
**25,384 XLR** (`engine_top.place.rpt`). So "logic elements" is
not a second, larger measurement - it is `LUT4 + FF + adder cells`, and the same
holds on Trion, where the exit-0 map gives 15,592 LUT4 + 8,301 FF = 23,893 and the
packer prints 24,854 LE. Always quote **FF and LUT4 separately, each with the run
it came from**, and never add a packer LE figure to a map cell count.
**Accepted bounded cost of the fix** (captain's ruling): writing the whole word makes
the weight RAM be written on *every* load cycle, redundantly re-writing the lanes
already filled. Functionally equivalent; the cost is activity/power. Recorded as a
**future optimisation candidate** (selective write, only when timing/area allow) and
deliberately **not** changed now - the whole-word write is what unlocked the Ti60F225
device measurement in the first place.

**The 43.6 MHz is not the MAC array.** The worst reported path
(`engine_top.timing.rpt`: 23.094 ns, **126 logic levels**) runs entirely inside
`layer_seq` - `seq/w_ev_r[2] -> seq/e_r`, the sequencer's combinational
event/address arbitration, including a wide carry chain (`seq/add_12`). The second
path is 0.496 ns / 2 levels. So the first frequency fix is to pipeline or
re-register that arbitration network; no data-path arithmetic has to change.

**Device capacity correction.** Efinity's own packer reports Ti60F225 as
`XLRs 60800`, `Memory Blocks 256`, **`DSP Blocks 160`** (`engine_top.place.rpt`),
and Efinix's product page says the same (logic elements 62016, **DSP blocks 160**,
https://www.efinixinc.com/shop/ti60.php). The planning figure used so far - 93
multipliers - is not this device's DSP count; per engine it is 50/160 = 31.25 %,
and the binding resource is logic, not DSP: **2 engines** fit (2 x 25,384 = 50,768
XLR = 83.5 %, 100/160 DSP, 156/256 RAM), 3 would not.

Cross-family check with the *fixed* RTL, `sh run_fixed.sh Trion T20F256 I3 trion`
(map exit 0, pnr exit 1 - T20F256 has 19,728 LE and 36 multipliers):
16,028 LUT4 / 4,101 ADD / 8,552 FF / 180 `EFX_RAM_5K` / **50 `EFX_MULT`** - the
same 50 multipliers as Ti60F225, so the number is a property of the RTL, not of a
family-specific mapper quirk.
## 3. The blocker was a Titanium-only toolpath bug, not bad RTL

The *same* file list maps on Trion and fails there only on device size (section
5.4 of `docs/engine/e5_resources.md`), so the RTL is synthesisable. `repro/` reduces the
Titanium failure to five small files; see `repro/run_repro.sh`:

| reproducer | Ti60F225 | Trion T20F256 |
|---|---|---|
| `ctrl_mult.sv` 8x8 signed multiply, registered | exit 0, `EFX_DSP24 x1` | exit 0, `EFX_MULT x1` |
| `ctrl_ram_narrow.sv` 64x8 RAM | exit 0 | exit 0 |
| `ctrl_ram_word.sv` 256x1152, whole-word write | exit 0 | exit 0 |
| `fail_ram_byteslice_const.sv` byte-lane **constant** write | `EFX-0103`, exit 59 | maps (exit 20: all logic optimised away) |
| `fail_ram_byteslice_var.sv` byte-lane **variable** write | `SIGSEGV`, exit 139 | maps (exit 0, non-fatal assert) |
| `fail_ram_byteslice_hier.sv` same RAM one hierarchy level down (the `layer_seq`/`engine_top` shape) | **`ram net has invalid dimension`, exit 12** - the exact assert that kills `engine_top` | maps |

Only one line of the engine has the failing shape:

```
conv_stream.sv:358:  wr[ld_t * NPASS + ld_oc / P][8 * (ld_oc % P)+:8] <= w_data;
```

i.e. the byte-lane write into the packed weight word (architecture.md section 6).
`conv_stream.sv:526` (`lb[...] <= x_pixel`) writes a whole 512-bit word and is fine.
**Fixed in t15** in the RTL itself: the word is assembled in a register and the RAM
is written whole (section 2b). The fix is behavioural-identity preserving - the load
contract is sequential, so lanes arrive 0..P-1 and lane 0 starts a fresh shadow;
unused lanes of a final partial block are now deterministic 0 instead of undefined,
and the compute side ignores them (`y_cnt` / `rq_pe_c` clamp to the layer's channel
count). Evidence: `sim/run_engine.sh` before and after the change produced
**byte-identical** dumps (52 files: 32 per-layer + 20 e2e) and identical gate lines.

## 5. Where the multipliers land (the question that decides the DSP budget)

`efx_map` prints `EFX-0666` / `SYN-0666` `Mapping into logic multiplier 'mult_N'`
for every multiply it implements in LE logic instead of a multiplier block. On the
Ti60F225 attempts there are exactly **eight** such warnings and they are all 32-bit
address arithmetic - none of them is a MAC lane:

| file:line | what it computes |
|---|---|
| `conv_stream.sv:233,234,235,237` | `win_w_c`, `win_h_c`, `k2_c`, `ld_end_c` - tile/stride/loop address math |
| `tile_reader.sv:118,119,129,130` | window/stride address math |

The identical eight warnings appear in the Trion run, and Trion still reports 50
hard multipliers for `engine_top` (37 for `conv_stream`) - so they are not the MAC.

Direct evidence from `probe/` (both runs **exit 0**, whole resource summary in the
probe's `outflow/*.map.rpt`):

| probe | Ti60F225 | Trion T20F256 |
|---|---|---|
| `mac_lane1.sv` - one signed int8 x int8 lane, 32-bit accumulate, registered | **`EFX_DSP24 x1`**, 32 ADD | `EFX_MULT x1`, 32 ADD |
| `mac_array32.sv` - 32 lanes + 32-input adder tree, registered | **`EFX_DSP24 x32`**, 945 ADD, 32 FF | `EFX_MULT x32`, 963 ADD |

**The MAC array does land in hard multiplier blocks on Ti60F225: P=32 costs 32 DSP**
(one per lane, exactly the architecture assumption). The 93-DSP account is
therefore sound; the corrected engine total is 50 multipliers (section 4), not 34.

Two side findings from the same probe round:

- The **frozen, bit-exact `conv_engine` (E3) cannot be built either**, and there the
  failure is *not* family-specific: `efx_map --root conv_engine` over
  `conv_engine.sv + requant_unit.sv + sat_add.sv` (it instantiates `requant_unit`)
  exits 1 with `Caught SIGSEGV` on **Ti60F225 and on Trion T20F256** alike
  (`conv_engine_map.log`). Its five memories are byte/word-wide with no byte-lane
  write, so this is a **second, independent** blocker. Candidates probed and
  excluded: asynchronous reads (`probe/async_read_ram{,_4k,_16k}.sv`, exit 0 at
  288/4096/16384 entries) and sheer size (a 1 Mbit byte RAM with a synchronous read
  maps on Ti60F225 as `EFX_RAM10 x128`, exit 0).
- The 8 `EFX-0666` warnings are emitted identically on both families and are the
  only soft multipliers in the design.

## 6. Methodology traps worth knowing before quoting a number

1. **`--flist` does not pin the synthesis root.** `efx_run <name> --flist f.f`
   lets `efx_map` choose the top level, and with several uninstantiated modules it
   picks one of them: `conv_engine + requant_unit + sat_add` produced
   `Top-level Entity Name : sat_add` and **exit 0** - a green run for the wrong
   block. Pass `--root <name>` (or `--map_opts=root=<name>`), and always read
   `Top-level Entity Name` out of `<design>.map.rpt` before quoting anything.
2. **Two timing models, two Fmax numbers.** `--timing_model I3` and
   `--timing_model C4` are both accepted, give identical resources and different
   Fmax: `tile_reader` 125.628 MHz (I3, 7.960 ns) vs 146.886 MHz (C4, 6.808 ns),
   `requant_unit` 396.354 vs 438.789 MHz, `point_add` 363.504 vs 405.022 MHz.
   `docs/engine/architecture.md` section 9 says I3; Efinity's own Ti60F225
   tutorial uses C4. Section 4 lists the model next to every number.
3. `-f full` is unusable on this machine (Efinity's bundled `ivl` aborts with a
   `libstdc++.so.6: version CXXABI_1.3.15` ABI error). `-f compile` and `-f pnr`
   are used instead.
4. `--pnr_opts=--sdc_file=X` is rejected by `efx_run_pnr.py` argparse
   (`argument --opt: expected at least one argument`). Without an SDC, `efx_pnr`
   auto-constrains the clock port to 1 ns and `*.timing.rpt` reports the maximum
   achievable period - which is the Fmax quoted here.
5. Quote the per-stage `map : PASS / interface : PASS / pnr : PASS` lines from the
   log, not just the aggregate exit code, and say which stage a number came from.
